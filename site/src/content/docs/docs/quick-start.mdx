This page takes you from a freshly installed archix to a declared, locked system with a few generations, one of which you've rolled back from. It takes about fifteen minutes, most of it reading what `archix init` found.

You need archix installed ([Installation](/docs/installation/)) and root access.

## Capture your system with `archix init`

You don't write your first config by hand. `archix init` reads your running system and writes a config and a lock that describe it exactly, down to the version of every installed package. It changes nothing on the machine except the config directory.

```console
$ sudo archix init
```

It opens a full-screen wizard in nine steps: Welcome, Config, Packages, System, Config files, Boot, Generations, Dotfiles and Review. Each step shows what init found and asks what it can't decide for you, with the recommended answer already chosen. You can go back and change any answer, and nothing is written until you press `enter` on Review. Here's the Packages step:

```text wrap=false
 archix init                                                  host desktop  ·  step 3 of 9

 ✓ 1 Welcome         │   Packages
 ✓ 2 Config          │   What's installed, and what happens to what isn't declared.
 › 3 Packages        │
   4 System          │   ✓ repos core, extra, multilib
   5 Config files    │   ✓ 86 packages declared, 3 from the AUR
   6 Boot            │   ✓ 2 Flatpak apps, locked to their installed commits: com.spotify.Client, org.mozilla.firefox
   7 Generations     │   · 2 dependencies that nothing needs any more: python-pip, rust
   8 Dotfiles        │   · Everything installed now is declared, so the first switch removes nothing.
   9 Review          │
                     │   ▌ Dependencies nothing needs any more
                     │       ● keep them (listed in ignored_packages)
                     │       ○ let the first switch remove them
                     │
                     │     Later, when you install something with plain pacman or yay
                     │       ● switch offers to declare it, and removes it if you say no (recommended)
                     │       ○ switch leaves it installed and only lists it
                     │
                     │     [x] Show each AUR build recipe and ask before trusting it
                     │
                     │     If a locked AUR version can't be built any more
                     │       ● ask, defaulting to the nearest newer version (recommended)
                     │       ○ take the nearest newer version
                     │       ○ take the nearest older version

 enter next  ·  esc back  ·  ↑↓ field  ·  ←→ choose  ·  1-9 jump  ·  q quit
```

The sidebar marks the steps you've seen with `✓` and the current one with `›`, and the header shows the host and the step. `▌` marks the field you're on. The bottom line lists the keys that work right now:

| Key | What it does |
| --- | --- |
| `enter` | Go to the next step. On Review, write the config. |
| `esc` | Go back a step. |
| `1`–`9` | Jump to that step. |
| `↑` `↓`, `tab` | Move between fields, or through a checklist. |
| `←` `→` | Change a choice, or flip a `[x]` setting. |
| `space` | Tick or untick the checklist entry under the cursor. |
| `a`, `n` | In a checklist, select all or none. |
| `r` | In Config files, go back to the recommended files. |
| `q`, `ctrl-c` | Quit without writing anything: `init was cancelled; nothing was written`. |

Answers stay as you left them when you move between steps. Text fields, the config location and the generation limits, take typing directly, so while you're in one, letters and digits (`q` and `1`–`9` included) go into the field; `tab` or `↑` `↓` moves on, and `ctrl-c` still quits. A step with a text field won't advance until the value is valid, and the problem shows above the key hints, such as `! the config directory must be an absolute path`.

What each step decides:

<Steps>

1. **Welcome.** What init found: how many packages to declare and how many come from the AUR, config files, user accounts and Flatpak apps. Nothing to answer.

2. **Config.** `Where should the config live?` is `/etc/archix` by default, but any directory works, such as a clone of your own repo. If you pick another directory, `/etc/archix` becomes a symlink to it, and a config in a directory you own is handed over to you, so you can edit it without `sudo`. When git is installed, `Make it a git repository` runs `git init` and `git add`; nothing is committed.

3. **Packages.** Your explicitly installed packages, from the repos and the AUR, are declared in `installed.lua`. Third-party repos in your `pacman.conf`, such as CachyOS's or chaotic-aur, are declared as they are, and init asks what to do if a locked package disappears from one (see [Third-party repos](/docs/guides/third-party-repos/)). Foreign packages that aren't on the AUR are left alone, in `ignored_packages`, with a `!` line. Orphaned dependencies can be kept in `ignored_packages` or left for the first switch to remove. `Later, when you install something with plain pacman or yay` sets [`undeclared_packages`](/docs/concepts/pacman-and-yay/#undeclared-packages). With AUR packages, there are also review and [missing versions](/docs/concepts/lockfile/#missing-versions). System-wide Flatpak apps are declared in `flatpak.apps`, with any remote other than Flathub, and locked to the commits they're installed at. Apps installed with `--user` are left out, and so are apps whose remote is gone, with a `!` line. See [Flatpak and AppImages](/docs/guides/flatpak-and-appimages/).

4. **System.** Hostname, timezone, locales and keymap, but only where the option would write exactly what's on disk now. Regular users (uid 1000 to 59999), each listed with uid, shell and groups, declared with their real groups, shell, home and description so declaring them changes nothing, and regular groups. Services whose enabled state differs from their preset, each listed as `on` or `off`. Nothing to answer; this step shows what gets taken over.

5. **Config files.** The `/etc` files you changed: package config files edited since they were installed, and files nobody owns in well-known directories such as `/etc/systemd/system`, `/etc/sysctl.d` and `/etc/udev/rules.d`. Files that hold secrets are never listed or copied, only counted. The rest is one scrollable checklist, each file tagged with why it's there: `recommended`, then `changed from its package's version` or `not from any package`. Recommended files, such as `/etc/fstab` and anything hand-written, start ticked; the others are mostly changed by package install scripts. See [Safety](/docs/concepts/safety/#what-init-captures-and-never-captures).

6. **Boot.** On a btrfs root, `Snapshot / before every switch, as an extra recovery point`. If systemd-boot is installed and your kernel command line has `root=`, the step shows the command line and offers `Write a boot entry for each generation`.

7. **Generations.** `Generations gc always keeps` (10) and `…and any younger than this many days` (30). Both have to be whole numbers.

8. **Dotfiles.** Opt-in. Pick a user if there's more than one, then tick entries from `~/.config` and top-level dotfiles; nothing is ticked by default. They're copied into the config's `home/` and declared as live links. See [Dotfiles and apps](/docs/guides/dotfiles-and-apps/#bringing-your-existing-dotfiles-in).

9. **Review.** Everything init will write, one line each: the config location, packages, undeclared and unused packages, Flatpak apps, accounts, services, config files, boot, snapshots, generations and dotfiles. `enter` writes it.

</Steps>

Then the wizard closes, and init prints the rest in the terminal. With AUR review on, it shows each AUR build recipe and asks before trusting it. It finds the Arch Linux Archive snapshot that matches the most installed versions and pins every package that differs from it, older ones included, so the lock is exactly what you have (see [The lockfile](/docs/concepts/lockfile/#how-init-picks-the-snapshot)). Then it shows what the first switch would change, which should be nothing:

```
── Lock ────────────────────────────────────────
  · finding the archive snapshot closest to what's installed
  ✓ 212 packages locked to the 2026-10-09 snapshot
  · held at their installed version instead: mesa
  ✓ 2 Flatpak apps locked to their installed commits

── Result ──────────────────────────────────────
  ✓ the system matches the lock and the config: the first switch changes nothing

  Config written to /etc/archix
    init.lua                          loads this host
    lua/hosts/desktop/init.lua        settings, users, services and files
    lua/hosts/desktop/installed.lua   packages; archix -S and -R edit it
    files/desktop/                    copies of the managed config files
    archix.lock                       the exact package versions

  Next: look it over, then run sudo archix switch
```

For scripts, `sudo archix init --defaults` takes every recommended answer without opening the wizard, so it needs no terminal. It ticks the recommended config files, brings in no dotfiles and doesn't make a git repository, and prints what it captured in Packages, System, Config files and Boot sections before the same Lock and Result.

There are two exceptions to an empty Result. Dotfiles you imported are listed, because the first switch backs up the originals and replaces them with links into the config. And if you let archix write boot entries, it declares the boot tooling it needs, `mkinitcpio` and `systemd-ukify`, so the Result lists them as installs if they're missing. Either way, the section starts with `! the first switch would still change these:`.

## Look at what you got

The config is laid out like a neovim config:

```console
$ tree /etc/archix
/etc/archix
├── archix.lock
├── init.lua
├── files
│   └── desktop
│       └── etc
│           ├── fstab
│           ├── mkinitcpio.conf
│           ├── pacman.d
│           │   └── mirrorlist
│           └── sysctl.d
│               └── 80-swappiness.conf
└── lua
    └── hosts
        └── desktop
            ├── init.lua
            └── installed.lua
```

`init.lua` imports the host that matches your hostname. `lua/hosts/<hostname>/init.lua` holds what init captured:

```lua title="lua/hosts/desktop/init.lua"
-- Written by `archix init` from this machine; edit it freely.
return {
  hostname = "desktop",
  timezone = "Europe/Berlin",
  repos = { "core", "extra", "multilib" },
  ignored_packages = { "nvidia-dkms-custom" },
  flatpak = { apps = { "com.spotify.Client", "org.mozilla.firefox" } },
  users = {
    me = { uid = 1000, groups = { "wheel" }, shell = "/usr/bin/zsh", description = "Me" },
  },
  services = { ["bluetooth.service"] = true, ["sshd.service"] = true },
  files = {
    ["/etc/fstab"] = { source = "files/desktop/etc/fstab" },
    ["/etc/sysctl.d/80-swappiness.conf"] = { source = "files/desktop/etc/sysctl.d/80-swappiness.conf" },
    -- ...
  },
  kernel_params = { "root=UUID=0a3c5e1f-6b2d-4f7a-9c8e-1d2b3a4c5e6f", "rw", "quiet" },
  boot = { loader = "systemd-boot", microcode = { "amd-ucode.img" } },
}
```

Your explicitly installed packages, from the repos and the AUR, are in `installed.lua`. The file is yours to edit freely; `archix install` and `archix remove` add and remove names there too, as its first line says. Dependencies aren't listed; the lock records them.

```lua title="lua/hosts/desktop/installed.lua"
-- This host's packages. Edit freely; `archix install` and `archix remove` add and remove names here too.
return {
  packages = {
    "base",
    "firefox",
    "linux",
    -- ...
  },
}
```

`archix.lock` holds the snapshot date and every package's exact version. Packages that didn't match the snapshot are listed under `pinned`, and Flatpak apps get their own table with the commit each is installed at:

```toml title="archix.lock"
[hosts.desktop]
date = "2026-10-09"
repos = ["core", "extra", "multilib"]
declared = ["archix", "base", "firefox", "linux", "mkinitcpio", "neovim", "steam", "systemd-ukify"]
pinned = ["mesa"]

[hosts.desktop.packages]
firefox = { version = "144.0-1", repo = "extra", file = "firefox-144.0-1-x86_64.pkg.tar.zst", sha256 = "37895f9d195203f4981ee730bec23c4079d10b5b53fc2c3e69db37c1bfed1257", explicit = true }
# ...

[hosts.desktop.flatpak]
"com.spotify.Client" = { remote = "flathub", ref = "app/com.spotify.Client/x86_64/stable", commit = "5f8806197a2b3c4d6e8f0a1b2c3d4e5f60718293a4b5c6d7e8f9012a3b4c5d6e" }
"org.mozilla.firefox" = { remote = "flathub", ref = "app/org.mozilla.firefox/x86_64/stable", commit = "0bb3a9e40c1f8d2e4b6a7c9d1e3f5a7b9c0d2e4f6a8b1c3d5e7f9a0b2c4d6e8f" }
```

git is optional, but worth it. When the config directory is a git repo, every generation records the commit it was built from. If you said yes to git, `init` already ran `git init` and `git add`, so commit now, from the config directory (with `sudo` if it's the root-owned `/etc/archix`):

```console
$ git add -A && git commit -m "Capture desktop with archix init"
```

## The first switch

```console
$ sudo archix switch
boot entry for the new generation
apply 1 change? [Y/n]
:: installing packages
...
:: writing the boot entry
:: making the new generation current
switched to generation 1 (snapshot 2026-10-09)
```

No packages change. On a machine where archix writes boot entries, the only change is generation 1's boot entry. Without boot entries, the switch prints `switched to generation 1 (snapshot 2026-10-09); no package changes were needed`. Either way, the files archix took over are backed up first, so taking one out of the config later puts the original back. Your system looks the same as before, but now it's described, locked and reversible.

## Make a change

Add a package to your host file. Lists from every module are concatenated, so this adds to what's in `installed.lua`:

```lua title="lua/hosts/desktop/init.lua" ins={3}
return {
  hostname = "desktop",
  packages = { "htop" },
  -- ...
}
```

Ask archix what that would do before doing it:

```console
$ archix diff
resolving 87 declared packages against the 2026-10-09 snapshot
note: archix.lock is out of date for desktop; showing a fresh resolution
snapshot 2026-10-09: 213 packages
install    htop 3.4.1-1
```

The lock still has your old package set, so `diff` resolves the new one on the fly. `htop` comes from the same 2026-10-09 snapshot as everything else, so adding it doesn't upgrade anything else. That is the point of the snapshot.

Now switch:

```console
$ sudo archix switch
resolving 87 declared packages against the 2026-10-09 snapshot
+ htop 3.4.1-1
213 packages locked
wrote /etc/archix/archix.lock
install    htop 3.4.1-1
boot entry for the new generation
apply 2 changes? [Y/n]
downloading htop-3.4.1-1-x86_64.pkg.tar.zst
:: installing packages
...
:: making the new generation current
switched to generation 2 (snapshot 2026-10-09)
```

`switch` updated the lock for you, showed the changes, and applied them once you said yes. `sudo archix install htop` would have done the same, writing the name to `installed.lua` instead of your host file. Commit the change:

```console
$ git commit -am "Add htop"
```

## Update everything

To move to today's packages, update the lock to the newest archive snapshot, then switch. `update` only rewrites the lock; nothing is installed until you switch:

```console
$ sudo archix update
resolving 87 declared packages against the 2026-10-15 snapshot
snapshot 2026-10-09 -> 2026-10-15
~ linux 7.2.8.arch1-1 -> 7.2.9.arch1-1
~ mesa 1:25.3.0-1 -> 1:25.3.1-1
213 packages locked
wrote /etc/archix/archix.lock
$ sudo archix switch
...
switched to generation 3 (snapshot 2026-10-15)
```

You can also use `sudo archix -Syu`, or just `sudo archix`, which upgrades from your live mirrors like yay does and adopts the result into the lock. See [pacman and yay](/docs/concepts/pacman-and-yay/#archix--syu).

## Roll back

Say the new mesa breaks your games. Go back:

```console
$ sudo archix rollback
downgrade  linux 7.2.9.arch1-1 -> 7.2.8.arch1-1
downgrade  mesa 1:25.3.1-1 -> 1:25.3.0-1
roll back to generation 2 (snapshot 2026-10-09) with 2 changes? [Y/n]
...
rolled back to generation 2 (snapshot 2026-10-09); archix.lock is unchanged, so the next `archix switch` returns to the config
```

archix makes the system match generation 2 again: its exact package versions from the cache, its files, users and services. No rebuilds.

Rollback changes the system, not your config. Your `archix.lock` still says 2026-10-15, so the next `archix switch` would apply it again. To stay back, revert the lock in git, or move it with `archix update --to 2026-10-09`.

<Aside type="tip">
	If the system won't boot at all, pick generation 2 in the systemd-boot menu. archix rolls back to it early in boot. See [Generations and rollback](/docs/concepts/generations/#rolling-back-from-the-boot-menu).
</Aside>
